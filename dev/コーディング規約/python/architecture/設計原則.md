# 設計原則の優先順位

1. DRY — 最重視
2. SOLID — 重視（特に I と L）
3. 拡張性意識 — YAGNI は強制しない、先回り抽象化を許容

## DRY

- 同じロジック・データ・構造を何回書いたら共通化するかは `architecture/リファクタリング判断.md` の回数に従う
- ただし 3 箇所目以降のための過剰抽象化はしない（閾値は `architecture/リファクタリング判断.md`）
- テスト関数の本文には当てない（`testing/テスト戦略.md` の「テスト関数の書式」）

## SOLID

| 原則 | 適用                                                                         |
| ---- | ---------------------------------------------------------------------------- |
| S    | 1 関数 / 1 モジュールが複数の理由で変更されない                              |
| O    | 新 feature / 新 provider 追加時に既存変更不要                                |
| L    | Protocol 実装は構造的に等価（戻り値型・例外契約・副作用範囲）                |
| I    | 巨大 Protocol を作らず用途別に小さく（`AsyncChatFn` と `EmbedFn` は別 type） |
| D    | 高レイヤは低レイヤを関数の型エイリアスで抽象化                               |

## 拡張性

- 「いずれ来そう」な拡張ポイントは最初から関数の型で抽象化（後付けより安い）
- 「来るかわからない抽象化」は増やさない（Protocol / `@overload` の量産は逆効果）

## クラスと関数

関数ファースト。クラスを使うのは:
- DTO（`@dataclass` / `BaseModel`）
- ライブラリ要求（FastAPI Middleware、Pydantic 継承、CLI Command）
- 長期保持のランタイム状態（接続プール、WebSocket セッション）

サービス / Repository / Provider / Validator 等は関数で書く。

- 可変なモジュール変数を持たない。やむを得ず持つなら `_` 付きにし、関数を通して触る（定数は可）
- メタクラスの自作・属性の動的な差し込み・import の書き換え・`__del__` を使わない（標準ライブラリとライブラリが要求するものは可）
