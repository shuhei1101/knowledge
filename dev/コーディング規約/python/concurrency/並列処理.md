# 並列処理

GIL 前提で設計する（フリースレッド版・subinterpreters を使うときは、[Python のドキュメント](https://docs.python.org/3/howto/free-threading-python.html) と依存ライブラリで対応状況を確かめる）。

## 判断フロー

```
CPU バウンド？
├── No (IO) → asyncio が第一候補。古い sync lib なら ThreadPoolExecutor
└── Yes
    ├── 1 タスク 100ms 未満 → 並列化しない or numpy / numba で内部高速化
    └── 1 タスク 100ms 以上 → ProcessPoolExecutor
```

## 早見表

| やりたいこと                | API                                                                        |
| --------------------------- | -------------------------------------------------------------------------- |
| 多数の HTTP 並列            | `asyncio` + httpx.AsyncClient                                              |
| 同期 IO の並列（古い lib）  | `ThreadPoolExecutor`（GIL は IO 待ちで解放）                               |
| 重い計算の並列              | `ProcessPoolExecutor(max_workers=os.cpu_count())`                          |
| 既存 sync 関数を async から | `asyncio.to_thread`                                                        |
| 外部コマンド                | `subprocess.run(check=True)` / async なら `asyncio.create_subprocess_exec` |

## ProcessPoolExecutor の制約

- 引数 / 戻り値は pickle 可能であること（ラムダ / closure 不可）
- プロセス起動コストがあるため 1 タスク 100ms 以上が目安
- `if __name__ == "__main__":` ガード必須（Windows / macOS）

## 共有状態

共有状態はバグの温床なので避け、Producer / Consumer でキューに流すのが基本。必要なら threading.Lock / multiprocessing.Queue 等。multiprocessing でグローバル変数は共有されない（別プロセスは別物）。
