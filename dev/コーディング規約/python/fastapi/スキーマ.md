# 入出力 Pydantic スキーマ

- リクエスト / レスポンスは Pydantic、内部 DTO（`@dataclass`）とは分離
  - 理由: API スキーマは凍結したい / 検証の厳しさが違う / 公開フィールドの選択 / 命名形式の差を吸収
- 配置は `features/{feature}/schemas.py`（小規模なら `types.py` にまとめても可）
- 変換メソッドをスキーマ側に持たせて route をワンライナーにする
  - リクエスト側に `to_domain(self) -> DomainXxx`
  - レスポンス側に `@classmethod from_domain(cls, result) -> Self`

## Field

- `min_length` / `max_length` / `ge` / `le` / `pattern` で検証、`description` / `examples` で OpenAPI 記述
- 固定選択肢は `Literal[...]`（OpenAPI に enum として出る）
- カスタム検証は `@field_validator`（単一）/ `@model_validator(mode="after")`（横断）。ValidationError は FastAPI が 422 にマップ

## camelCase 対応

フロントが snake_case を受け入れられるならそのままが一番楽。必要なら `ConfigDict(populate_by_name=True, alias_generator=...)` + `Field(alias=...)`。

## response_model

`response_model=` で余計なフィールド除去・型検証・OpenAPI 反映が効くが、`from_domain` での明示変換のほうが読みやすいことが多い。

- 内部 DTO（`@dataclass`）を route 引数に直接使わない（Pydantic 検証が動かない）
