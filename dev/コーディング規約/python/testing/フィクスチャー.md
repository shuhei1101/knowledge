# Factory-as-Fixture パターン（DB リソース準備の推奨形）

シナリオテスト等で「複数インスタンスを作りたい」「引数付きでリソースを作りたい」ケースは、fixture が関数を返す構造にする。
値を返す fixture で名前をハードコードする（`user_a` 等）のは避ける。

- 1 fixture = 1 責務（`user_factory` / `profile_factory` / `task_factory` を分けて conftest.py に並置）
- 依存はテスト本体で引数として明示（`profile_factory(user_a)` の書式）
- cleanup は fixture 内で自動追跡し、`yield` の後で作成順の逆順に delete を回す

```python
@pytest.fixture
def user_factory():
    created = []
    def _create(name, role="user"):
        u = create_user(name=name, role=role)
        created.append(u)
        return u
    yield _create
    for u in reversed(created):
        delete_user(u.id)
```

- アンチパターン: `setup_all_scenario_x()` のような god setup で全リソース作らない（単一責務を保つ）
- アンチパターン: fixture 内で名前ハードコード（`user_a` 等）→ 常に factory を返す構造にする
- アンチパターン: `try/finally` で手動 cleanup を書く → fixture の `yield` に任せる
