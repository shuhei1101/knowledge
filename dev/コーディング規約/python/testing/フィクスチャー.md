### Factory-as-Fixture パターン（DB リソース準備の推奨形）

シナリオテスト等で「複数インスタンス作りたい」「引数付きでリソース作りたい」ケースは、**fixture が関数を返す** 形にする。
値を返す fixture で名前をハードコードする（`user_a` 等）のは避ける。

- **1 fixture = 1 責務**（`user_factory` / `profile_factory` / `task_factory` を分けて conftest.py に並置）
- **依存はテスト本体で引数として明示**（`profile_factory(user_a)` の形）
- **cleanup は fixture 内で自動追跡** → `yield` の後で作成順の **逆順 delete** を回す

```python
@pytest.fixture
def user_factory():
    created = []
    def _create(name, role="user"):
        u = create_user(name=name, role=role)
        created.append(u)
        return u
    yield _create
    for u in reversed(created):
        delete_user(u.id)

@pytest.fixture
def profile_factory():
    created = []
    def _create(user, visible=True):
        p = create_profile(user.id, visible=visible)
        created.append(p)
        return p
    yield _create
    for p in reversed(created):
        delete_profile(p.id)
```

テスト側は必要な factory だけ引数で要求:

```python
def test_multi_user(user_factory):
    a = user_factory("A")
    b = user_factory("B")
    # 終了時に b, a の順で自動 delete

def test_with_profile(user_factory, profile_factory):
    a = user_factory("A")
    p = profile_factory(a, visible=True)
    # 終了時に p, a の順で自動 delete
```

- **アンチパターン**: `setup_all_scenario_x()` のような god setup で全リソース作らない（単一責務を保つ）
- **アンチパターン**: fixture 内で名前ハードコード（`user_a` 等）→ 常に factory を返す形にする
- **アンチパターン**: `try/finally` で手動 cleanup を書く → fixture の `yield` に任せる（漏れ防止）
