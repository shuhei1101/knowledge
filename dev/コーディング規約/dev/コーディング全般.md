# コーディング全般における規約
<!-- ただし、各言語で固有のルールがある場合は、それを優先すること -->

## 例外ハンドル・エラーは握りつぶさない
- 例外ハンドル try-exceptなどはオーバーに実装しすぎないこと
  - 必要のある場面のみ例外は実装すること（何でもかんでも例外ハンドルを付けるべきではない。意味のある場合のみ実装しよう）
- 例外をもし実装する場合、握りつぶさないこと（エラーで画面が落ちてよい。落ちた方が開発者がすぐ気づけ、放置を防げる。）
- 例外は最小原則の法則で
  - ログを出すための例外はOK

## フォールバック仕様
- 特定の読み込みが失敗したときのフォールバック値などは極力設けない。
  - これを設けると、ログを見ない限り、設定が正しく読まれているかどうかが気づきにくい
  - 通常は読み込まれる前提で作るべき。
  - 読み込まれない=ソースコードや環境の不具合のため気づけるようにエラーとすべき
  - フォールバックは基本的に使わない

## 定数関連
- 定数はハードコードせず、置き場所を [設定値の置き場所](../../判定フローチャート/設定値の置き場所.md) で決めて外だしする

## ソースコード内コメント
- コメントに履歴・経緯・背景は書かない
  - NG例: `PRXXXで編集`、`ISSUE-Nで修正`、`旧 xxx～`、`QAxxxで...`、`以前は xxx だったが yyy の理由で変更`、`〜という経緯でこの実装にしている`
  - 基本的にその時点でスナップショットとなるコメントを記載する（コードにはコードの現在の動作だけを書く）
  - 昔の履歴はgitlogで確認できるため、不要
- 設計書・ドキュメントへの参照は書かない
  - NG例: `仕様は dev/設計書/xxx.md を参照`、`SoT は xxx.md`
  - 一部の設計書だけをリンクすると「書かれたものだけが仕様」と誤認させる（他の設計書からも参照されている可能性がある）
  - 実装から仕様を探すときは関数名・論理名の grep で設計書側から逆引きする
  - リンクの方向は 設計書 → 実装 の一方向のみ

- コメントは 日本語 で書く
  - ただし、特殊な環境（windowsの .bat とか）は日本語だとバグるので注意。そのほかは基本的に日本語で。
- 関数には 1 行 docstring を必ず書く
- 関数内のforやif文などインデントが深くなるとこはインラインコメントを残す
- 複雑な処理はインラインコメントを残す
  - インラインコメントは該当行の上でもいいし、横でもいい。見やすい方で。

## 汚いコード禁止
- デッドコードは禁止です
  - ファイル編集時にデッドコードは削除してください。
- マジックナンバー禁止

## 外部コマンド・パス・データの読み込み
- 外部コマンドは、ライブラリで済むなら呼ばない。呼ぶときは引数を配列で渡し、シェルを通さない
- 外部から来た値をコマンドの引数にするときは、オプションと読まれないよう `--` の後ろに置く（コマンドが対応している場合）
- 外部から受け取った名前でファイルのパスを組むときは、解決した後に基準のフォルダの配下にあることを確かめる
- 外部から来たデータを、読み込むだけでコードが動く形式・関数で読まない（Python なら `pickle` と `yaml.load` を使わず `yaml.safe_load`）

## タイムスタンプ
- タイムスタンプ表示は JST (Asia/Tokyo) 統一。UTC のまま画面・ログに出すと
  - 「昨日のデータに見える」誤認を確実に起こす

| 場所                                                                  | 規約                                                                        |
| --------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **ストレージ** (`*.jsonl` / `*.yaml` / DB)                            | UTC タイムゾーン付き ISO8601 (`2026-05-24T05:18:02+00:00`) — 標準慣行を維持 |
| **UI 表示** (HTML / dev 画面)                                         | **JST に変換** (`05/24 14:18:02 JST` 形式)                                  |
| **CLI / バッチログ** (ユーザーが目で見るログ)                         | JST タイムゾーン付き or UTC でも `+00:00` 明示                              |
| **コミット message / PR タイトル / コメント** | **JST 日付** で表現 (例: 「2026-05-24 に発生した障害」)                     |
