# Rate Limiting

第一選択は Upstash Ratelimit（Redis ベース・Edge 対応）。`@upstash/ratelimit` + `@upstash/redis`、env は `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN`。

## 構成

- `app/(shared)/lib/ratelimit.ts` に用途別 limiter を定義（`prefix` で分離）
  - 用途別の上限値はプロジェクトの非機能要件で決める
- アルゴリズムは `slidingWindow` を既定とする。バースト許容なら `tokenBucket`
- 全体適用は proxy.ts（`/api/` パスで IP キーに `limit()`、超過は 429 + `X-RateLimit-*` / `Retry-After` ヘッダ）
- 特定エンドポイント（ログイン等）はさらに route.ts 内で厳しめに適用

## キー設計

- IP だけだと同一ネットワークで誤検知 → ログイン済みは `userId` ベース（`userId ?? ip:{ip}`）
- アクション別制限（1 時間に 5 投稿等）は `post:{userId}` のようなキー + `fixedWindow`
- 重い処理は cost 指定（`limit(key, { rate: 10 })`）

## クライアント側

429 は `RateLimitError`（`RATE_LIMIT`）に変換し、`handleAppError` が長め toast を出す（`shared/エラークライアントハンドラー.md`）。

## 運用

- dev / prod で別 Redis データベース（dev は高めに設定）
- Bot 対策が必要なら Vercel Firewall / Cloudflare Turnstile（ログイン・登録・問い合わせ）
- 短時間に多発する 429 はログで監視
