# フロントエンド テスト戦略

単体・結合・E2E の 3 層で持つ。
テストの対応関係は設計書（モジュール構成 / フロントエンド結合 / シナリオ）のテスト表が SoT で、テストは表と 1:1 で実装する。
React Testing Library・DB は使わない。

| 層   | ツール                            | 見るもの                                              | 配置                          |
| ---- | --------------------------------- | ----------------------------------------------------- | ----------------------------- |
| 単体 | vitest（jsdom）                   | 純関数・状態・派生計算・フォーマッタ                  | `tests/unit/`（src をミラー） |
| 結合 | vitest（jsdom）+ MSW / fetch stub | 1 画面操作 = 1 ファイル（入力 → API 呼出 → DOM 反映） | `tests/integration/screens/`  |
| E2E  | playwright                        | 画面が組み上がるか・主要操作フロー                    | `tests/e2e/{name}.spec.ts`    |

- 単体の単位 = 1 ファイル。
  同一ファイル内のヘルパーは実物のまま、ファイル外の依存は Mock する（Sociable）
- 単体は分岐ごとに 1 テスト以上置き、分岐カバレッジを極力 100% にする
- 結合はバックエンド API を Mock する（実通信しない）
- ピラミッド構造: 単体で網羅し、E2E は重要フローだけ。
  E2E で単体・結合レベルを検証しない

## テスト関数の書式

- テスト名（`test` / `it` の説明文字列）は `{関数名}_when_{条件}` とし、期待値は名前に入れない（期待値が変わるたびに名前が変わるため）。
  条件分岐のない唯一のケースは `{関数名}` のみ
- 何を確認するか（設計書テスト表の概要 + 正常系 / 異常系）はテスト直前のコメントに書く
- 関数内を `// 準備` → `// 実行` → `// 検証` の順のコメントで区切る。
  例外検証のように実行と検証が一体になる場合は `// 実行・検証` にまとめる

```ts
// 19 歳は未成年と判定する（正常系）
test("is_minor_when_age_19", () => {
  // 準備
  const user = new User({ age: 19 });
  // 実行
  const result = user.isMinor();
  // 検証
  expect(result).toBe(true);
});
```
