# テンプレート: 非機能要件

外部コンポーネントの制約を踏まえてアプリとして守る値（コンポーネントをまたいで効く要件だけ）。1 プロジェクト 1 ファイル。

## 項目

<!-- table: data -->

| 名前 | title | 型 | 必須 | 選択肢 | 制約 | description | examples |
| --- | --- | --- | --- | --- | --- | --- | --- |
| title | タイトル | string | 必須 | - | - | `非機能要件`。 | - |
| lead | 冒頭リード | string | - | - | - | 対象を 1〜3 行で説明する。<br>初回に書いた内容のまま保ち、後から情報を足さない（仕様は各項目に書く）。<br>対象そのものが変わったときだけ書き換える。 | - |
| requirements | 一覧 | array | 必須 | - | minItems: 1 | 外部の制約から逆算したアプリの値。決まっていない項目も同じ一覧に置き、決定値を `未確定` にする。<br>未確定だった項目が決まったら同じ要素を書き換える。 | - |
| requirements[].name | 項目 | string | 必須 | - | - | 何についての値か。1 項目 = 1 要素。 | - |
| requirements[].english_name | 英語名 | string | - | - | pattern: ^[a-z0-9_]+$ | テスト関数・ファイルの名前に使う。 | - |
| requirements[].category | カテゴリ | string | 必須 | - | - | 性能 / レート制限 / 可用性 / 耐障害 / セキュリティ / コスト / 保守性 / 動作環境 等。<br>動作環境は対応端末・OS・ブラウザ・画面サイズ・入力方式・通信を 1 項目ずつ置く。 | - |
| requirements[].external_constraint | 外部の制約 | string | 必須 | - | - | 外部が示す上限・下限・保証値。自主基準は `制限なし`、分からなければ `未確定`。 | - |
| requirements[].source_kind | 出所種別 | string | 必須 | 外部 API の制限 / 外部ライブラリの制限 / 実行基盤の制限 / PC 性能 / ユーザー要望 / 制限なし / 未確定 | - | 6 種類を 1 つずつ突き合わせ、どれにも当たらないときだけ `制限なし`。 | - |
| requirements[].source | 出所 | string | - | - | - | 外部の制約を書いた設計書の参照・資料の URL・ユーザーの回答コメントの URL。 | - |
| requirements[].value | 決定値 | string | 必須 | - | - | 実装とテストが参照する値。まだ決められないときは `未確定`。 | - |
| requirements[].unit | 単位 | string | - | - | - | - | - |
| requirements[].rationale | 根拠 | string | 必須 | - | - | 外部の制約そのままでない理由。未確定なら何が分かれば決まるか。 | - |
| requirements[].measurement | 測り方 | string | - | - | - | 実機での確認に回す項目は、確かめる端末と操作を書く。 | - |
| requirements[].test_file | 対応テスト | string | - | - | pattern: ^tests/.+ | 非機能要件テストのファイル（`tests/nfr/test_{英語名}.py`）。測れない項目・実機での確認に回す項目は持たない。 | - |
| requirements[].verification | 確認の記録 | object | - | - | - | 実機での確認に回した項目だけが持つ、確かめた結果。確かめた人が書く。<br>修正の後に合格の記録を持たない項目は、確かめ直して書き換える。 | `{"device": "Windows 11 の PC の Edge", "version": "Edge 140", "date": "2026-10-05", "result": "合格"}` |
| requirements[].verification.device | 端末 | string | 必須 | - | - | 確かめた端末（OS・ブラウザなど）。 | - |
| requirements[].verification.version | 版 | string | 必須 | - | - | 確かめた端末の版（OS・ブラウザの版）。 | - |
| requirements[].verification.date | 確認日 | string | 必須 | - | pattern: ^[0-9]{4}-[0-9]{2}-[0-9]{2}$ | `YYYY-MM-DD`。 | - |
| requirements[].verification.result | 合否 | string | 必須 | 合格 / 不合格 | - | - | - |
| requirements[].verification.detail | 確認内容 | string | - | - | - | 不合格のとき、起きた事象。 | - |
| requirements[].overflow | 超過時の挙動 | string | - | - | - | 決定値を超えたときに何が起きるか（分割 / 待機 / リトライ / エラー）。黙って切り捨てない。起こり得ないときは持たない。 | - |
| requirements[].breakdown | 内訳 | array | - | - | - | 決定値に至る積み上げ（外部の上限からの差し引き、または内側の値の合計）。積み上げの無い項目は持たない。 | - |
| requirements[].breakdown[].part | 区分 | string | 必須 | - | - | - | - |
| requirements[].breakdown[].value | 値 | string | 必須 | - | - | - | - |
| requirements[].breakdown[].notes | 補足 | string | - | - | - | なぜその値か。 | - |
| requirements[].tests | 非機能要件テスト | array | - | - | - | 測れない項目・未確定の項目は持たない。 | - |
| requirements[].tests[].name | テスト名 | string | 必須 | - | pattern: ^test_[a-z0-9_]+$ | `test_{英語名}_when_{条件}`（条件分岐の無い唯一のケースは `test_{英語名}`）。 | - |
| requirements[].tests[].summary | 概要 | string | 必須 | - | - | - | - |
| requirements[].tests[].condition | 条件 | string | 必須 | - | - | 入力・負荷・回数を数値で。決定値の境界を 1 行以上入れる。 | - |
| requirements[].tests[].measurement | 測定方法 | string | 必須 | - | - | - | - |
| requirements[].tests[].expected | 期待値 | string | 必須 | - | - | 合否の判定の基準。 | - |
| requirements[].tests[].notes | 補足 | string | - | - | - | - | - |
| requirements[].refs | 関連 | array | - | - | - | - | - |
| requirements[].reason | 理由 | string | - | - | - | そうしている理由。読み手の判断が変わるものだけを書く。 | - |
| requirements[].status | 状態 | string | - | planned / implemented / deprecated / removed | - | 項目の状態。`planned`（予定）/ `implemented`（実装済み）/ `deprecated`（非推奨）/ `removed`（廃止）。書かなければ実装済みとして扱う。 | - |
| requirements[].visibility | 公開 | string | - | user / developer | - | 公開の範囲。`user`（ユーザー向け）/ `developer`（開発者向け）。<br>書かなければ親の値を引き継ぎ、最上位の既定は `developer`。 | - |
| requirements[].implementation | 実装 | string | - | - | pattern: ^[^#\s]+(#\S+)?$ | 実装の場所。リポジトリの直下からのファイルのパスに、`#` とシンボルの名前を続けてよい。 | `src/app/features/profile/service.py#update_profile` |
| requirements[].introduced | 導入 | object | - | - | - | 入ったバージョンと PR。 | - |
| requirements[].introduced.version | バージョン | string | - | - | - | 入ったバージョンのタグ（例 `v0.3.0`）。 | - |
| requirements[].introduced.pr | PR | integer | - | - | - | 入れた PR の番号。 | - |
| requirements[].aliases | 別名 | array | - | - | - | 検索で当てたい言い換え。 | - |
| requirements[].notes | 補足 | object | - | - | - | 項目に分けられない残り。節の名前 → 本文。<br>同じ名前の節が多くの設計書に出たら、標準の項目へ格上げする候補になる。 | - |
| refs | 関連 | array | - | - | - | - | - |
| notes | 補足 | object | - | - | - | 項目に分けられない残り。節の名前 → 本文。<br>同じ名前の節が多くの設計書に出たら、標準の項目へ格上げする候補になる。 | - |

## 記載例

```yaml
title: 非機能要件
lead: 外部の制約から逆算したアプリの決定値。
requirements:
- name: 入力トークン上限
  english_name: input_limit
  category: 性能
  external_constraint: 100 万トークン
  source_kind: 外部 API の制限
  source: dev/設計書/外部API/OpenAI#
  value: 10 万
  unit: トークン
  rationale: 内部のシステムプロンプトと出力枠を差し引く
  measurement: API へ渡ったトークン数を数える
  test_file: tests/nfr/test_input_limit.py
  overflow: |-
    上限を超える入力は送信の前に分割する。
    分割できない単一のメッセージが超えたときは古い履歴から切り詰め、それでも収まらなければエラーにして呼び出し元へ返す。
  breakdown:
  - part: 外部の上限
    value: 1,000,000
    notes: モデルのコンテキストウィンドウ
  - part: 出力枠
    value: 64,000
    notes: 最大出力トークン
  - part: アプリの決定値
    value: 100,000
    notes: 入力として受け付ける上限
  tests:
  - name: test_input_limit
    summary: 上限ちょうどの入力
    condition: 100,000 トークンの入力を 1 回送る
    measurement: API へ渡ったトークン数
    expected: 分割されずに 1 回で送られる
  - name: test_input_limit_when_over
    summary: 上限を超えた入力
    condition: 100,001 トークンの入力を 1 回送る
    measurement: API へ渡ったトークン数
    expected: 2 回に分かれ、各回が 100,000 以下
- name: 応答の待ちの上限
  english_name: response_wait_limit
  category: 耐障害
  external_constraint: 制限なし
  source_kind: 制限なし
  value: '30'
  unit: 秒
  rationale: 内側の待ち 2 つの合計に余裕を足す（入れ子の待ち）
  measurement: 内側の待ちを両方とも上限まで遅らせた要求を 1 回送り、応答までの時間を測る
  overflow: 上限を超えたら呼び出し元へタイムアウトのエラーを返す。回復は呼び出し元のリトライで待つ
  breakdown:
  - part: 内側の待ち（外部 API の呼び出し）
    value: '10'
    notes: 外部 API の実測 p99.9 + 余裕
  - part: 内側の待ち（保存）
    value: '10'
    notes: 保存の実測 p99.9 + 余裕
  - part: 余裕
    value: '10'
    notes: 実測が無いため内側の待ちの合計の 50% を仮に置く
  - part: アプリの決定値
    value: '30'
    notes: 内側の待ちの合計 + 余裕
- name: 同時接続数
  category: 性能
  external_constraint: 未確定
  source_kind: 未確定
  value: 未確定
  rationale: 想定利用者数が決まる「利用者管理」の要件が確定してから決める
- name: 対応ブラウザ
  category: 動作環境
  external_constraint: Chrome と Edge の最新版
  source_kind: ユーザー要望
  source: https://github.com/{owner}/{repo}/issues/{番号}#issuecomment-{ID}
  value: Chrome と Edge の最新版
  rationale: 利用者が社内の PC だけで使うため
  measurement: Chrome と Edge の実機で、全ての画面の操作を最後まで完了できるかを確かめる
  verification:
    device: Windows 11 の PC の Edge
    version: Edge 140
    date: '2026-10-05'
    result: 合格
- name: 最小画面幅
  english_name: min_viewport_width
  category: 動作環境
  external_constraint: '360'
  source_kind: ユーザー要望
  source: https://github.com/{owner}/{repo}/issues/{番号}#issuecomment-{ID}
  value: '360'
  unit: px
  rationale: スマホでは閲覧できれば足りる
  measurement: ブラウザの表示幅を変えて全ての画面を開き、横スクロールの有無を見る
  test_file: tests/nfr/test_min_viewport_width.py
  tests:
  - name: test_min_viewport_width
    summary: 最小幅での表示
    condition: 表示幅 360px で全ての画面を開く
    measurement: 文書の横幅と表示幅
    expected: 全ての画面で文書の横幅が 360px 以下
```

  category: 動作環境

  source_kind: 未確定
  value: 未確定
