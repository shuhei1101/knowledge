# 要件

## 要望

knowledge を汎用の開発ドキュメントサーバー dev-docs（[shuhei1101/dev-docs](https://github.com/shuhei1101/dev-docs)）の配信元として使えるようにし、使い方のページを書き直す。
knowledge は自分のサーバー・文書の MCP のプラグイン・そのためのマーケットプレイスを持たず、直下に `dev-docs.yaml`・スキーマ・検査と変換のスクリプトだけを置く（規約『ドキュメント管理』の `delivery-04`、『MCP サーバー作成ルール』の `registration-04`）。
dev-docs のプラグインが配る `http://127.0.0.1:${DEV_DOCS_PORT:-8781}/mcp` の 1 つから、ツールの引数 `source` で knowledge を指す（`registration-05`）。
利用者の流れは次のとおり。

1. `/dev-docs:global-setup` で端末を準備する
2. `/dev-docs:setup {knowledge のクローンのパス}` で、端末の設定 `~/.config/dev-docs/settings.yaml` の `sources[]` に knowledge を登録する（`scope.read` は全ての作業場所、`scope.write` は knowledge のクローンと worktree だけ）
3. 画面で文書を読み、Claude Code から dev-docs の MCP のツール（`search_docs`・`write_docs`・`delete_docs`・`describe`・`list_changes`・`trace_related`）に `source: knowledge` を渡して文書を検索・取得・書き込みする

dev-docs.yaml のメタデータは D-171 の形で書く（[#51 の本文](https://github.com/shuhei1101/knowledge/issues/51) の冒頭の注記が正）。
documents の行は `type`・`custom`・`defaults[]` を持たず、front matter も読まない。`metadata` は列の対応だけで、`alias_type` は行の属性にする。
YAML でない文書（Markdown・ソースコード）は、各フォルダの `files.yaml` の行にパス・タグ・説明を書く（D-173〜D-177、規約『ドキュメント管理』の `files-yaml-01`〜`files-yaml-04`）。
タグのマスターは持たない（D-169）。
この Issue の完了を shuhei1101/ai-monitor#3093（AI Monitor の手順書の規約の読み方を `search_docs(source: knowledge)` に置き換える）が待っている。

knowledge の設計書（アーキテクチャ図・シナリオ・インターフェース定義・モジュール構成など）の置き場所は A にした（初期構築で決め、[reviewer の合格](https://github.com/shuhei1101/knowledge/pull/72#discussion_r4430471302)）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | ai-monitor の設計書の置き場所（`dev/設計書/`）と Schema に置き、ai-monitor の書くツール（`write_design_doc_*`）で書く | エージェントの設計・照合・レビューの手順と道具がそのまま使える | 『ドキュメント管理』の `folder-01`（文書は `docs/` 1 つに置く）から外れる |
| B | 『ドキュメント管理』に合わせて `docs/` に種類（`design` など）を追加し、`schemas/` に Schema を置いて `dev-docs.yaml` の `documents[]` で配る | knowledge の規約と揃い、dev-docs の画面と MCP で設計書も読み書きできる（A-25 の例も `docs/design/` に置く） | ai-monitor の書くツールと設計書の検証が使えない |


ai-monitor の照合・レビューの手順は `dev/設計書/` と書くツールを前提にしており、dev-docs を ai-monitor が使うようになる（D-101）までは、その前提に合わせる方が手戻りが少ない。

### 確かめ方

- dev-docs の検査（`/dev-docs:setup` の点検）が knowledge の `dev-docs.yaml`・`files.yaml`・スクリプトに誤りを返さず、全ての種類の文書が Markdown に変換できる
- `/dev-docs:setup` で登録すると、画面で develop の全ての文書が開ける
- knowledge のクローンの外の作業場所から、`search_docs` に `source: knowledge` を渡すと knowledge の文書が返る
- knowledge のクローンの外の作業場所から `write_docs` を呼ぶと、`scope.write` の外として書き込まずに返る
- 書き込みのツールが、検査のスクリプトに通らない内容を書かずに `isError` で返す
- CI が、違反のある YAML を含む PR で失敗する

## 影響するユースケース

既存のユースケースは無く、全て新規。
画面・MCP・起動の振る舞いは dev-docs のユースケースで、knowledge のユースケースはそれを knowledge の設定とスクリプトで使う流れを扱う。

| 種別 | ユースケース | 影響 | 依存 |
| --- | --- | --- | --- |
| 複合ユースケース | 利用者が端末に knowledge を導入して規約を引く | 新規（`/dev-docs:global-setup`・`/dev-docs:setup` での登録から、画面と MCP での検索・取得まで） | 利用者が dev-docs に knowledge を登録する, エージェントが knowledge の文書を検索・取得する |
| 単一ユースケース | 利用者が dev-docs に knowledge を登録する | 新規（`/dev-docs:setup` での `sources[]` への追加・`scope.read`・`scope.write`・点検） | |
| 単一ユースケース | 利用者が画面で knowledge の文書を読む | 新規（`nav` のタブ・サイドバーと、変換した本文） | 利用者が dev-docs に knowledge を登録する |
| 単一ユースケース | エージェントが knowledge の文書を検索・取得する | 新規（dev-docs の MCP に `source: knowledge` を渡す。`files.yaml` の行の Markdown・ソースコードも含む） | 利用者が dev-docs に knowledge を登録する |
| 単一ユースケース | エージェントが knowledge の文書を書き込む | 新規（`scope.write` の内でだけ書き込み、書き込みのときに検査のスクリプトを通す） | 開発者が文書の違反を検査する |
| 単一ユースケース | 開発者が文書の違反を検査する | 新規（検査のスクリプトと CI） | |

## スコープ外

<!-- table: data -->

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| 汎用の開発ドキュメントサーバー（画面・文書の MCP・設定・検査・変換）と、文書の MCP を配るプラグイン | dev-docs が受け持つ（D-96・D-100、規約『MCP サーバー作成ルール』の `registration-03`） | 対応済み（shuhei1101/dev-docs#3・#4） |
| フック用のプラグイン `knowledge@knowledge` とマーケットプレイス（`.claude-plugin/`） | 規約の「プラグインとマーケットプレイスを持たない」は文書の MCP のためのもので、フック用は対象外 | 変更しない |
| AI Monitor の手順書の規約の読み方を `search_docs(source: knowledge)` に置き換える | AI Monitor の側の作業 | shuhei1101/ai-monitor#3093 |
| GitHub Pages を Actions のワークフローで `visibility: public` の文書だけ配信する形へ切り替える | 配信先（master）と契機がこの Issue と違う | #69 |
| 入力に用語の文脈を足す mod（A-16） | 照合する語を YAML から直接読む別のプラグイン（D-88）で、knowledge は `dev-docs.yaml` の行の `alias_type` を置くまで | 起票予定 |
| 文書を書き込む MCP ツールに、文書の書き方の規約（ドキュメント管理・タグと用語の登録など）を rule-inject で当てる | 規約と索引の側の作業 | #67 |
| 『規約の索引を当てる』の手順の廃止 | rule-inject がファイルを触ったときに規約を案内する仕組みは、MCP で置き換わらない | 予定なし |
