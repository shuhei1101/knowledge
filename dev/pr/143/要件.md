# 要件

## 要望

Web の画面のボタンのラベルの決まりを、新しい規約『ボタンのラベル』（`docs/rule/ui-button-label.yaml`）に記載する。
起点 Issue の決定の 6 件を、次のとおり入れる。

| # | 決まり | 入れ方 |
| --- | --- | --- |
| 1 | アイコンだけにしてよいのは、標準的で意味が 1 つに決まる操作（閉じる・戻る・検索・メニュー・コピー など）と、ツールバー・表の行のように場所が詰まっている操作 | 新しい規約に記載する |
| 2 | 主要な操作・破壊的な操作・確認ダイアログのボタン・合うアイコンが無い操作は、文字を出す（アイコンの併用は可） | 新しい規約に記載する |
| 3 | アイコンだけのボタンには、ツールチップを必須にする（ホバーとフォーカスで出す） | 新しい規約に記載する |
| 4 | 同じ操作は画面全体で同じアイコンにし、アイコンは 1 つのセットから選ぶ | 同じ操作に同じアイコンを当てる決まりを新しい規約に記載し、1 つのセットから選ぶ決まりは既存の規約『情報の階層と見た目』（`visual-consistency-01`）への参照にする |
| 5 | ボタンの文言は操作を表す動詞にし、「OK」「はい」「いいえ」ではなく結果が分かる言葉にする。キャンセルは「キャンセル」に統一する | 既存の規約『入力と文言』（`wording-01`・`wording-term-format-02`・`wording-operation-02`）への参照にする。例は『入力と文言』に合わせて「削除」「保存」とする（ユーザーの回答: [確認事項](https://github.com/shuhei1101/knowledge/issues/142#issuecomment-6594878142) の案 A） |
| 6 | 同じグループの中では、アイコンの有無を統一する | 新しい規約に記載する |

決まり 3 を入れるため、『共通コンポーネント規約』のアイコンボタンの「決めるべき観点」から「ツールチップ必須化」を削除する（必須かはプロジェクトで決める観点ではなくなる）。
変える項目の外の文言は一字一句そのまま残す（規約『既存文章の維持』）。
変えたページは `rev` を 1 つ上げ、`last_reviewed` を変えた日にする。

`未確定`: 新しい規約を `rules.yaml` に載せるか（決める段: ドキュメント修正）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 載せない。`related` で『操作とアクセシビリティ』・『入力と文言』・『情報の階層と見た目』から辿れるようにする | 同じ scope:ui の『操作とアクセシビリティ』・『入力と文言』・『情報の階層と見た目』と扱いが揃う。画面のファイルを触るたびの注入が増えない | 画面のファイルを触るときに自動では読まれない |
| B | `paths` を `**/*.{tsx,jsx,html}` にして載せる | ボタンを作るときに自動で読まれる | 他の ui の規約は載っておらず、この規約だけが注入される |

推奨: A

規約『ルール索引への登録』の判断は ui の規約の全体で揃えるべきで、この規約だけを先に載せると扱いがばらつく。

## スコープ外

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| 『入力と文言』の `wording-term-format-02` の「する」の有無 | ユーザーが既存の規約に合わせる案 A を選び、変更しない | 予定なし |
| 押せる領域を全て 44 x 44 にする | 起点 Issue で見送った（今の『操作とアクセシビリティ』・『レイアウト』の基準が WCAG 2.2 に沿っている） | 予定なし |
| タイトルの大文字化・末尾の「…」 | 起点 Issue で見送った（英語の UI の慣習） | 予定なし |
| 破壊的な操作の赤の使い分け | 起点 Issue で見送った（確認ダイアログの部品の規約の範囲で足りる） | 予定なし |
| visionOS・macOS のツールバーの表示の切り替え | 起点 Issue で見送った（Web の画面には当たらない） | 予定なし |
| 『業務画面のUI要素』の行ごとの操作（3 つ未満はアイコンボタン） | 決まり 1 の「表の行のように場所が詰まっている操作」と食い違わず、変更が要らない | 予定なし |
