## 変更方針

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| 案内の場面の判定 | `docs/` の全ての文書を、要件.md の `### 案内の場面の判定` の表で判定し、文書 1 件を 1 行にした表（文書の ID・種類・強制注入の 4 つの基準の結果・仕組み・`paths` か `tools`・`args`・`aliases`・`inject_when`）をこの計画書の `### 判定の表` に記載する | 判定の表の記載をドキュメント修正の前のレビューに回す |
| rules.yaml | 判定の表で `paths` か `tools`・`args` になった文書のエントリを追加し、4 つの基準を満たさなくなった既存のエントリを除外する | glob の記載方法は規約『ルール索引への登録』の `paths の記載`。追加後に rule-inject の MCP の索引のチェックで問題 0 件を確認する |
| タグと用語の登録 | `dev-tag-term-registration` のエントリに `**/docs/**/*.yaml` と、`tools` に `mcp__*__write_docs`・`mcp__*__write_design_doc*`・MindStella の `add`・`update`・`batch` を追加し、`on` に `mcp` を含める。`args` では絞らない | 規約の本文が 4KB を超える場合は、強制注入の基準 4 に合わせる方法をインターフェース定義設計で決める。MindStella のツールの完全名は MindStella の配信元で確認する |
| aliases | 判定フローチャート『エイリアスの登録』の候補（略称・英語名・旧名・会話や Issue で呼んだ名前・一般語のタイトル）を文書ごとに列挙し、判定表『エイリアスを登録しない条件』で判定した名前を記載する | 衝突の確認は全ての文書の `name`・`aliases` と、配信元の用語（`alias_type: term`）の両方で確認する |
| inject_when | 一般語のタイトル（「フォルダ構成」「Security」「YAML」など）で特定の文脈でだけその文書を指す文書に、規約『フィルター・照合条件の構造』の構造で記載する | 条件の `field` は `text`、`op` は `contains`・`not_contains` |
| スキーマ | `schemas/common.schema.yaml` の `metadata` に `inject_when` を追加し、`examples` を記載する | 構造は規約『フィルター・照合条件の構造』の条件と束（`and`・`or`・`not`）。入れ子は 3 レイヤーまで |
