# 要件

## 要望

knowledge の全ての文書（`docs/` の rule・template・flowchart・decision-table・guide・skill・changelog・word-list）について、案内する場面を判定し、判定のとおりに `rules.yaml` と文書のメタデータへ登録する。

### 案内の場面の判定

文書ごとに、次の表の上の行から順に適用して、案内の仕組みを決める。
判定の結果は、文書ごとに 1 行の表で `文書.md` に記載する。

<!-- table: data -->

| 文書 | 案内する場面 | 仕組み |
| --- | --- | --- |
| 規約『ルール索引への登録』の強制注入の 4 つの基準を全て満たし、編集するファイルが決まる | そのファイルを編集する前 | `rules.yaml` の `paths` |
| 4 つの基準を全て満たし、MCP のツールで書き込む文書・Issue・PR・コメントに適用する | そのツールを呼ぶ前 | `rules.yaml` の `tools`・`args`（`on` に `mcp` を含める） |
| 4 つの基準を満たさない（任意で参照する） | 会話・指示にその話題が出たとき | 文書の `aliases`・`inject_when`（alias-inject） |

<!-- /table -->

- スタック別の規約（Next.js・HTML・React・Python）も knowledge の `rules.yaml` に記載する。プロジェクト側の索引は knowledge のルールを指せない
- `aliases` は判定フローチャート『エイリアスの登録』と判定表『エイリアスを登録しない条件』で判定する。一般語の名前で、特定の文脈でだけその文書を指すもの（React の『フォルダ構成』など）は、`inject_when` を規約『フィルター・照合条件の構造』の構造で記載する
- 4 つの基準を満たさなくなった `rules.yaml` の既存のエントリは除外し、その文書は `aliases` で案内する
- R-5 の案の「常に守る要点（セッションの開始・SessionStart）」の行は使わない。#135 で『単語の選び方』の SessionStart の注入をやめ（slop-check へ移った）、#154 で SessionStart に文脈を入れない決定をしたため

### 文書を書き込むときの規約『タグと用語の登録』（#67 の統合）

- 規約『タグと用語の登録』（`dev-tag-term-registration`）を、文書の YAML のファイルの編集（`**/docs/**/*.yaml`）と、MCP の書き込み（dev-docs の `write_docs`・ai-monitor の `write_design_doc_*`・MindStella の `add`・`update`・`batch`）に適用する
- MCP の書き込みは `tools` だけで適用し（`on` に `mcp` を含める）、`args` で絞らない。タグを付け忘れた書き込みでも規約を案内するため
- 『ドキュメント管理』『YAML ファイルの単位』は D-92 で任意と判定したため `rules.yaml` で適用せず、`.md` にも適用しない

### 照合条件 `inject_when` を記載できるようにする（alias-inject#61 の統合）

- `schemas/common.schema.yaml` の文書のメタデータに `inject_when`（規約『フィルター・照合条件の構造』の条件と束）を追加し、スキーマの検査に合格させる
- 変換（`knowledge-markdown`）は `inject_when` を本文に出さない（`aliases` と同じく内部向けのメタデータ）
- `inject_when` は文書の一番上のキーに記載する。alias-inject は `metadata` に書かないキーを同じ名前の列から取るため、`dev-docs.yaml` の `metadata` には対応を記載しない

### 終わりの条件

- `文書.md` の判定の表に、`docs/` の全ての文書の行がある
- rule-inject の MCP の索引のチェックで、knowledge の `rules.yaml` の読めないエントリ・JSON Schema への違反・実在しない `rule`・当たらない `paths` が 0 件
- 全ての文書の検査（`uv run --frozen --script scripts/check_all.py`）で違反が 0 件
- rule-inject の MCP のルールの検索で、`write_docs` の呼び出しに規約『タグと用語の登録』がヒットする
- alias-inject で、「フォルダ構成」「Security」「YAML」を含み、その文書の文脈を含まない本文に、その文書が注入されない

`未確定`: 全ての文書を 1 つの PR で見直すか、種類ごとに PR を分けるか（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 全ての文書を、この PR で種類ごとに commit を分けて見直す | `aliases` の衝突（ほかの文書の name・aliases に既にあるか）を全ての文書で一度に確認できる | 差分が大きく、レビューが長くなる |
| B | 種類ごと（rule の領域ごと・template・flowchart ほか）に PR を分ける | 1 つのレビューが短い | `aliases` の衝突の確認を PR ごとにやり直す。後の PR が前の PR の `aliases` と衝突しうる |

推奨: A

`aliases` の判定は文書どうしの衝突の確認を含み、全ての文書を並べた 1 つの表で判定するほうが漏れない。

### `read_tool` の記載

- knowledge の文書を指す `rules.yaml` の全てのエントリに `read_tool`（dev-docs の `search_docs` に文書の ID を指定する参照の方法）を記載する（TH-60 の要望）
- 端末に入っている rule-inject（0.2.3）は `read_tool` を許さないキーとして索引を丸ごと読まない。`read_tool` を入れた commit（[shuhei1101/rule-inject#102](https://github.com/shuhei1101/rule-inject/pull/102)）を含む rule-inject の版が端末に入るまで、`read_tool` の記載を待つ（依存）。`paths`・`tools`・`aliases`・`inject_when` の記載は待たずに進める
