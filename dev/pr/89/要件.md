### #79: 設計原則・デザインパターン

`dev/設計原則`（D-67）を新設し、対象を `.py`・`.ts`・`.tsx` に限る。
パターンは `dev/デザインパターン` に分ける。
A-12 の原則の表から次を書く。

- YAGNI を既定にし、外部との境界（HTTP・SDK・DB・storage・時刻・ID の生成）だけ最初からアダプターにする。内部は実装が 2 個になるまで抽象化しない（D-65）
- 知識（業務ルール・定数・スキーマ・API 型）は 1 回目から、コードの見た目の重複は 3 回目で共通化する。共通化した関数に分岐用の引数が増えたらインラインに戻す（D-66）
- 複雑さの lint は新しいリポジトリで error、既存の Python は warn から（D-68）
- 行数の基準は置かず、SLAP と cognitive complexity だけにする（D-69）。Python で cognitive complexity を測る道具（ruff の C901 は McCabe）は、ドキュメント修正の段で確かめて書く
- デザインパターンはアダプター・ストラテジー（関数を渡す）・デコレーター・ファサードを載せ、採用しないパターンは記載しない（D-70）
- ボーイスカウトルールは触った関数の中だけ。周辺のリファクタリングは別の commit にする（D-71）
- React の規約・typescript/ の共通化の記述（`next/` の component-catalog の「3 回目」など）は、D-65・D-66 と食い違わないようにそろえる

`未確定`: `dev/設計原則` を rules.yaml に登録するか（決める段: ドキュメント修正のレビュー）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `**/*.{py,ts,tsx}` で `on: [write]` に登録する | D-67 の「コードを書くときだけ読まれる」がそのまま効く | 1 ファイルの編集で当たる量が増える（A-16 の基準で 4KB 以内に収める） |
| B | 登録せず、タグで任意に読む | 注入の量が増えない | コードを書くときに読まれる保証が無い |

推奨: A

A-16 の基準は拡張子だけの glob を全言語共通の規約 1〜2 件に許しており、設計原則はそれに当たる。

### #74: MCP・YAML の規約

ワークスペース `tmp/mcpベストプラクティス検討` の決定を、dev-docs の名前に依らない一般の決まりとして書く。
置き場所は既存の『MCP サーバー作成ルール』（`docs/rule/claude-mcp.yaml`）・『YAML』（`docs/rule/dev-yaml.yaml`）・『claudeプラグイン』（`docs/rule/claude-plugin.yaml`）・『フック』（`docs/rule/claude-hook.yaml`）の該当のセクションを見て決める。

| 決まり | 決定 | 置き場所の候補 |
| --- | --- | --- |
| MCP の書き込みのツールは、呼んだセッションの作業ツリー（PreToolUse フックが引数に入れる）のファイルを書き換えるだけで commit しない | D-105 | dev-yaml の `MCP からの書き込み` |
| 他のリポジトリへ書き込めるかは、端末の設定の作業場所ごとの権限（読める・書ける作業場所の glob）で決める。Git のリポジトリへはそのクローンか worktree で作業中のときだけ書き、書く先はその作業ツリー。Git 管理外の書き込み先は権限に当たればどの作業場所からも書ける | D-111・D-134 | dev-yaml の `MCP からの書き込み` |
| 常駐の MCP サーバーはプラグインで配る。起動・管理は systemd --user を主にし（立て方は #82 の規約で書くため、ここでは「立て方は tmux・systemd の規約で定める」とだけ書く）、SessionStart のフックは落ちていたときの起動の補助、状態の確認・再読込・再起動・更新はサーバー自身が出す管理の MCP ツールで行う | D-100（#74 のコメントの D-82 の見直し） | claude-mcp の `sdk-transport-06` |
| フック・mod が文脈を追加するために MCP を呼んで届かないときは、何も追加せずに入力をそのまま渡す | D-74 | claude-hook か claude-mcp |
| 設定の YAML は、まとまり（文書・検査・変換など）を配列にし、主キーの `id` でつなぐ。ファイルの指定は `paths[]` にファイルか glob を並べる | D-115 | dev-yaml |
| リポジトリと一緒に変わる設定はリポジトリの設定ファイル（Git の中）に、端末ごとの選択は `~/.config/{名前}/settings.yaml` に置き、端末の設定はリポジトリの設定ファイルのパスを指す | D-106 | dev-yaml か claude-plugin の `設定ファイル` |
| 複数のリポジトリが読む YAML の形は、1 つのリポジトリが `schemas/{種類}.schema.yaml` を正本として持つ。ほかはスキーマだけに依存し、正本のリポジトリのタグを指定して取り込みバージョンを記録する。形を変えるときは正本のリポジトリに Issue を立て、ほかは取り込むバージョンを上げる | D-120 | dev-yaml の `スキーマ` |
| 設定ファイル（リポジトリの設定・端末の設定）に `version`（最後に移し替えたツールのバージョン）を持たせ、ツールはバージョンごとの移し替えの手順（`migrations/{バージョン}/`）を持つ。古い設定は手順を示して移し替えてから使い、設定のほうが新しければツールの更新を案内して止まる | D-156 | dev-yaml か claude-plugin の `設定ファイル` |

既存の近い決まりとは、対象を書き分けて食い違わないようにする（task-reviewer の任意の指摘）。

| 既存の決まり | 書き分け |
| --- | --- |
