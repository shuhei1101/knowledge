# 要件

## 要望

1. 規約『表し方の優先順位』に「キーの表」のグループを追加し、設定ファイル・スキーマのキーを表にするときの書式を定める

   | 決まり | 内容 |
   | --- | --- |
   | 列 | キー・型・必須・説明・例（設計書のテンプレートでは使用先の列も追加する） |
   | オブジェクト | 表を分けず、`steps[].tools[].args` のように `.` と `[]` でつないで 1 つの表に並べる |
   | 見本 | 表の後に、実際の値のコードブロックを付ける |

2. キーの表を手で記載するとき、1 の決まりを注入する
3. シナリオ・インターフェース定義などの種類の資料を手で記載するとき、その種類のテンプレート（スキーマの `required`）を注入する
4. 2・3 の条件を今の注入の仕組みで記載できなければ、その仕組みのリポジトリへ条件の追加を起票する

注入の仕組みは rule-inject の `rules.yaml` の行にする。

| 書き込みの経路 | 注入の条件 |
| --- | --- |
| Write・Edit で `.md` を書く | 今の行（`paths` の `**/*.md`）で規約『表し方の優先順位』がヒットする。キーの表の書式は、この規約に追加するだけで注入される |
| MindStella の資料を `add`・`update` で書く | `tools` と `args` の `re:` で、`item.body_markdown` のキーの表の見出しの行に規約『表し方の優先順位』を、`item.title` の種類の名前に種類のテンプレートを適用する |

alias-inject の `inject_when` は採らない。
照合するのは入力の文とツールの結果で、書き込みの中身を照合せず、案内も名前と概要だけのため。

## スコープ外

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| Write・Edit で書く `.md` の資料への、種類のテンプレートの注入 | パスで種類が分からず、書き込みの中身を条件にする必要がある。rule-inject の書き込みの中身で止める機能は、利用者の判断で対応しないと決まっている（[rule-inject#89](https://github.com/shuhei1101/rule-inject/issues/89)） | 予定なし |
| シナリオ・インターフェース定義のほかの種類のテンプレートの注入 | 手で記載する資料で必須の項目が漏れると挙がったのはこの 2 種類だけ | 予定なし |
| ワークスペース `何でも会話` の CLAUDE.md の「キーの表」の行の削除 | このリポジトリの外のファイルで、Issue の後続として利用者が削除する | 予定なし |
| 設計書のスキーマの各キーの使用先の列の値 | キーの使用先は [#217](https://github.com/shuhei1101/knowledge/issues/217) が扱う。この PR は列を設けることだけを決める | [#217](https://github.com/shuhei1101/knowledge/issues/217) |
| `rules.yaml` の、`write_docs` の `kind` にヒットするスキーマを案内する行 | 設計書を MCP で書き込む経路は [#194](https://github.com/shuhei1101/knowledge/issues/194) が扱う。この PR は手で記載する資料を扱う | [#194](https://github.com/shuhei1101/knowledge/issues/194) |
