# 要件

## 要望

dev-docs の画面で規約『文章の書き方』を開くと、`word-choice-table-02` のマーカー `<!-- embed: word-list-ai-slop -->` の位置に、対応表 `word-list-ai-slop` の `entries` の表が出る。

- 表は、対応表の文書を画面で開いたときの表（`render_word_list` の `| NG | OK |` の表）と同じ書式にし、`pattern`・`allow`・`examples` の値は出さない
- 対応表の行を追加・変更したら、規約の文書を書き換えなくても、画面の表が対応表の今の中身になる
- マーカーの無い文書の変換の結果は変わらない
- 指した文書が無い・対応表でないマーカーは、変換を失敗させず、その位置に展開できない理由を出す

展開する場所は、knowledge の converter（`knowledge_markdown.py`）にする（インターフェース定義設計で確定）。
converter が `<!-- embed: {文書の ID} -->` を ID の対応表の NG・OK の表に置き換え、`dev-docs.yaml` の `knowledge-markdown` を `cache: false` にする。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | converter で展開し、`knowledge-markdown` の行を `cache: false` にする | knowledge の作業 PR で完結し、表の書式を対応表の画面と同じにできる。設定の行が 1 つのまま | 全ての種類の文書で、開くたびに converter を起動する |
| A' | converter で展開し、同じ `run` で `cache: false` の converters の行を追加して `rule` の行だけに指定する | 控えを使わない範囲をマーカーを持つ種類に限定できる | 同じ `run` の行が 2 つになり、他の種類にマーカーを置くときは行の指定を変える必要がある |
| B | マーカーを dev-docs の書き方 `<!-- embed: docs/word-list/word-list-ai-slop.yaml#entries -->` に書き換え、dev-docs の展開に任せる | コードを変えない。展開は変換の控えの後で毎回行われる | `entries` の全てのキーが列になり、照合の正規表現・例文（`pattern`・`allow`・`examples`）まで規約の本文に出る |
| C | dev-docs に、文書の ID を指す埋め込みの機能を追加する（dev-docs へ起票） | 表の書式を対応表の画面と同じにでき、控えの問題も起きない | knowledge の作業 PR で完結しない |

採用: A

converter の 1 回の起動は `convention-writing-style.yaml` で 0.17〜0.34 秒（3 回の実測）で、非機能要件の 1 文書あたりの処理時間（20 秒）に対して十分に小さく、控えを使わない範囲を限定する利点が設定の行を増やす手間を上回らない。
