# 要件

## 要望

Python の規約のタイムアウト・リトライの値を、規約『資源の値の決め方』と判定フローチャート『タイムアウトの決め方』に沿わせ、入れ子の待ちの関係を満たすようにする。

### 今の値と導き方の食い違い

| 導き方 | 今の値で計算した結果 | 食い違い |
| --- | --- | --- |
| リトライ（各回のタイムアウト + 間隔 × 回数が外側の待ちに収まる） | 30 秒 × 4 回 + 間隔 1・2・4 秒 = 127 秒。`retry_after` で `wait_max` まで待つと 30 秒 × 4 回 + 30 秒 × 3 回 = 210 秒 | 外側の 60 秒に収まらない |
| 入れ子の待ち（外側 ≥ 内側の待ちの上限の合計 + 余裕） | `stamina-retry-01` は stamina の `timeout` を外側の `@with_timeout` と同じ秒数にする | 余裕が 0 |
| リトライの回数の上限 | `attempts=4` の既定のバックオフは 4 秒台で終わる | `wait_max=30.0` はバックオフの上限として機能せず、`retry_after` の打ち切りと `LlmServerError` の Retry-After にだけ影響する |
| 入れ子の待ち | Instructor の `max_retries=3` は、stamina の 1 回の試行の中で LLM を最大 4 回呼ぶ | 各回のタイムアウトの計算に入っていない |

### 変える値

| 文書 | 項目 | 値 | 変えること |
| --- | --- | --- | --- |
| `python-llm-exception-retry` | `stamina-retry-01` | `attempts=4, timeout=60.0, wait_initial=1.0, wait_max=30.0, wait_jitter=0.2` と「`timeout` は外側の `@with_timeout` の秒数に揃える」 | 導き方に合う関係へ修正する |
| `python-llm-exception-retry` | `timeout-01` | `AsyncOpenAI(timeout=30)` + `@with_timeout(seconds=60)` | クライアント（各回）→ stamina（全試行）→ デコレータ（全体）の入れ子の関係と、それぞれの導き方を記載する |
| `python-core-decorator` | `handler-decorator-02` | `@stamina.retry(on=<フック関数>, attempts=4)`・`@with_timeout(seconds=60)` | `stamina-retry-01`・`timeout-01` と同じ値の持ち方にする |
| `python-core-decorator` | `composition-01` | `@with_timeout(seconds=60)`・`@stamina.retry(on=retry_on_llm_error, attempts=4)` とコメントの「全体 60 秒」「3 回まで」 | 同上 |
| `python-llm-structured-output` | `instructor-02` | `max_retries=3` | 回数の導き方を添え、stamina の 1 回の試行に含まれる待ちとして `timeout-01` の入れ子に入れる |
| `python-fastapi-auth-error` | `exception-handler-01` | `LlmServerError` の Retry-After に `wait_max` を返却する | `wait_max` を導き直した後に、「上流の 5xx からの回復を待つ間隔」の意味と合うかを確認する。合わないときは Retry-After の導き方を修正する |

LLM の呼び出しの各回のタイムアウトは、判定フローチャート『タイムアウトの決め方』で判定した結果（利用者・上流が応答を待つ呼び出しと、バッチなど自分の処理の完了を待つだけの呼び出し）ごとに導き方を記載する。
規約の例の数字は名前（`<全体の待ち>` など）に置き換え、値の導き方と入れ子の式を `timeout-01` に 1 か所だけ記載する。
`python-core-decorator`・`python-llm-structured-output` は名前と `timeout-01` への参照だけを持つ。

LLM の API の公開仕様に応答時間の値は無く、公開されている値は非ストリーミングの 1 回の呼び出しの上限だけで、利用者が応答を待つ呼び出しの例の値にならない。
呼び出し元の待ちと実測もプロジェクトごとに違うため、全てのプロジェクトに当てはまる数字が無い。

### 共通

- 改めた文書の `rev` を 1 つ上げ、`last_reviewed` を変えた日にする
- 変える項目の外の文言は一字一句そのまま残す（規約『既存文章の維持』）

## スコープ外

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| 規約『自動保存』の `debounceMs`（既定 1000ms）、規約『handleAppError』の `RateLimitError` の toast の 5 秒 | 画面の操作の感触を決める値で、タイムアウト・リトライではなく、導出の元になる外部の上限や下流が無い | 予定なし |
| 規約『並列処理』の 1 タスク 100ms の判定 | 並列化の手段を選ぶ判定の閾値で、資源の値ではない | 予定なし |
| 各プロジェクトでの LLM の呼び出しのレイテンシの実測 | knowledge は LLM を呼ばないため、実測は規約を使用するプロジェクトの作業になる | 予定なし |
