# 要件

## 要望

文書を書く AI が、用語と関連（`related`）を登録するかを、文書 1 つに向かって順に当てる判定フローチャートで決められるようにする（react移行計画の D-108・D-110）。
タグはマスター（語彙）を持たない前提で書く（mcpベストプラクティス検討の D-169）。
変更する項目以外の文言は一字一句そのまま残す（規約『既存文章の維持』）。

### 判定フローチャートの新設（`docs/flowchart/`）

テンプレート『判定フローチャート』（`docs/template/template-flowchart.yaml`）と規約『判定フローチャート』（`docs/rule/markdown-flowchart.yaml`）の書式で、`kind: flowchart` の YAML を 2 つ作る。
タグは既存の判定フローチャートと同じ `scope:判定フローチャート`（`main: true`）を付ける。

- `docs/flowchart/flowchart-term-registration.yaml`（用語の登録）: 次の順に判定する
  - 登録するか: 規約『タグと用語の登録』の `term-register-01`・`term-not-register-01` の条件（プロジェクト固有の呼び名か・一般と違う狭い意味か・調べた外部のライブラリやサービスの名前か / 一般的な意味のままの技術用語か・1 文書の中だけの語か）
  - 置き場所: 複数のリポジトリで同じ意味で使うなら knowledge、1 つのリポジトリだけで使うならそのリポジトリ
  - 既存の用語との重なり: 同じものの別の言い方なら、新しい用語にせず既存の用語の `aliases`（使ってよい言い方）か `avoid`（やめた言い方）に入れる
- `docs/flowchart/flowchart-related-link.yaml`（関連の張り方）: 次の順に判定する
  - 張るか: `when`（いつ読むか）を 1 文で書けるか・本文でリンクしている相手と重ならないか（規約『ドキュメント管理』の `related-04`）
  - `type`: `requires`・`references`・`replaces`・`part_of`・`change_together` を判定の順に並べ、各 `type` の定義を図の直下の `※N` に書く
  - 片側か両側か: `change_together` だけ両側に書き、ほかは片側（規約『ドキュメント管理』の `related-03`）

`未確定`: `type` を判定する順（決める段: ドキュメント修正）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | Issue に書いた順（`requires` → `references` → `replaces` → `part_of` → `change_together`）で判定する | Issue の記述のまま | `references`（読むと判断の材料が増える）は他の 3 つにも当てはまるため、先に当てると `replaces`・`part_of`・`change_together` に届かない |
| B | 当てはまる範囲の狭い順（`replaces` → `part_of` → `change_together` → `requires` → `references`）で判定する | どの `type` にも届き、最後の `references` が受け皿になる | Issue に書いた順と変わる |

推奨: B

フローチャートは YES で離脱する判定を上から当てるため、広い条件を先に置くと後ろの `type` が選ばれない。

### 規約からの参照

- 規約『タグと用語の登録』（`docs/rule/dev-tag-term-registration.yaml`）
  - `related` に `flowchart-term-registration`（`requires`、用語を登録するか決めるとき）を追加する
  - 用語を登録する・しない条件の表（`term-register-01`・`term-not-register-01`）から、用語の判定フローチャートを参照する。表は例として残す
  - エイリアスを登録する・しない条件の表（`alias-register-02`・`alias-not-register-01`）から、alias-inject の判定フローチャート [エイリアスを登録するかを決める](https://github.com/shuhei1101/alias-inject/blob/develop/docs/%E4%BD%BF%E3%81%84%E6%96%B9/%E3%82%A8%E3%82%A4%E3%83%AA%E3%82%A2%E3%82%B9%E3%82%92%E7%99%BB%E9%8C%B2%E3%81%99%E3%82%8B%E3%81%8B%E3%82%92%E6%B1%BA%E3%82%81%E3%82%8B.md)（[alias-inject#32](https://github.com/shuhei1101/alias-inject/pull/32) で develop に入った）を参照する。リポジトリが違い ID で参照できないため URL で書く。表は例として残す
- 規約『ドキュメント管理』（`docs/rule/dev-document-management.yaml`）
  - `related` に `flowchart-related-link`（`requires`、関連を張るか決めるとき）を追加する
  - 関連の項目（`related-01`〜`related-04`）から、関連の判定フローチャートを参照する

### 配信

knowledge の文書として dev-docs で配信し、タグで引けるようにする。
rule-inject では注入しない（`rules.yaml` に載せない。D-110）。

| タグの付け方の判定フローチャートと、規約『タグと用語の登録』のタグの語彙の項目の書き直し | タグは別の Issue が持つ（同じファイルを触るため、計画で並列にしない組になっている） | #85 |

| 新しい文書を作るか既存の文書を直すか・documents の行の判定フローチャート | D-110 で判定の対象を持つ dev-docs に置くと決めた | [shuhei1101/dev-docs#18](https://github.com/shuhei1101/dev-docs/issues/18) |
| knowledge に共通の用語を置くファイル（用語集）の新設 | knowledge にはまだ用語集のファイルが無い（規約『ドキュメント管理』の `folder-05` のフォルダ構成の例に `terms.yaml` があるだけ）。フローチャートは置き場所をリポジトリの単位で判定し、ファイルは最初の共通の用語を登録するときに作る | 予定なし |
| 新しい判定フローチャートを `rules.yaml` に載せる | rule-inject では注入しない（D-110） | 予定なし |
