# 要件

## 要望

master へのマージ（push）で動く GitHub Actions のワークフローを新設し、GitHub Pages の配信元をブランチの `/docs` から Actions の成果物へ切り替える。

- 成果物に入れる文書は、`dev-docs.yaml` の `documents` が指す文書のうち `visibility: public` のものだけにする
- 文書は、[#51](https://github.com/shuhei1101/knowledge/issues/51) で入った変換のスクリプト `scripts/knowledge_markdown.py` で mdmark の記法の Markdown にし、mdmark で HTML にする
- 成果物には YAML の原本・スキーマ・`visibility: internal` の文書を入れない。成果物の中に `.yaml` のファイルが 1 つも無いことをワークフローで確かめ、あれば配信せずにジョブを失敗させる
- 公開の文書から `visibility: internal` の文書を指す参照は、Pages の中のリンクにせず、GitHub の master の YAML へのリンクにする
- 変換か HTML 化が 1 件でも失敗したら、配信せずにジョブを失敗させる（前に配信したサイトはそのまま残る）
- 手で動かし直せるよう、ワークフローは手動の起動（`workflow_dispatch`）も受ける

`未確定`: mdmark を CI で入れる方法（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | mdmark のリポジトリをタグを指定して checkout し、コミット済みの `dist/cli.js` を node で呼ぶ | npm へ公開していなくても使え、バージョンをタグで固定できる | checkout の手順が 1 つ増える |
| B | `npx github:shuhei1101/mdmark#{タグ}` で呼ぶ | 手順が 1 行で済む | `prepare` などのスクリプトが CI で走るかが package.json の書き方で変わる |

推奨: A

mdmark は `private: true` で npm に公開しておらず、`dist/` をコミットしているので、ビルドを挟まずにタグで固定した CLI を確実に呼べる。

`未確定`: 公開の文書を 1 枚の HTML にまとめるか、文書ごとのページにするか（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | mdmark の `build`（`kind: bundle`）で 1 枚の HTML にまとめる | mdmark の既存の機能だけで済み、文書間のリンクが HTML の中で辿れる | 公開の文書が増えると 1 枚が重くなる |
| B | 文書ごとに `export_html` で HTML を作り、目次のページを置く | 文書ごとの URL を持てる | 目次とリンクの書き換えを knowledge が持つ |

推奨: A

公開の文書は少なく、1 枚にまとめても重くならず、knowledge が持つ処理を最小にできる。

## スコープ外

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| 各文書の `visibility` の見直し（どの文書を公開にするか） | 要望は配信の仕組みの切り替えで、公開範囲は各文書のメタデータが決める | 予定なし |
| 変換のスクリプトの出力の書式の変更 | 使うだけで変更しない（#69 の `## 依存`）。リンクの書き換えは Pages の成果物を作る側で行う | 予定なし |
| develop の開発ドキュメントサーバーでの配信 | #51 で完了している | 予定なし |
