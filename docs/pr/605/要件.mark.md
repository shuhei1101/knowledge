# 要件

## 要望

画面設計（`schemas/design/screen.schema.yaml`）と部品設計（`schemas/design/component.schema.yaml`）に、規約にあるのに記載する欄が無い決まりの欄を追加し、種類ごとの必須・禁止を検査で求める。
スキーマと規約の更新が全て develop に入ったら、画面設計書を持つ監視対象の各プロジェクトへ、新規のスキーマで設計書を記載し直す Issue を起票する。

- Issue の表の 12 分類（状態の保持・ペイン・ボタンのアイコン・PC とスマホの出し分け・文言の量・表の機能・タブ・閉じ方・押した後の振る舞い・URL の履歴・ショートカット・画面全体の振る舞い）を、全てスキーマの欄か `x-rules` にする。欄の名前と構造は Issue の「足す欄の案」を起点に決め、追加する enum は英語にする
- 文言の量（分類 5）は欄にせず、`label` と `hint` の `x-rules` から規約（`ui-input-wording#wording-01`・`#wording-term-format-02`・`ui-information-hierarchy#information-hierarchy-01`）を参照する。`hint` を記載できる種類は入力の種類だけにする
- 要素の `items` は `additionalProperties: false` のまま、追加する欄を全て `properties` に並べ、#603 の `kind` を判別子にした `allOf` の `if` / `then` で、#600 から移した種類ごとの必須・禁止を `required` と `{欄: false}` で指定する
  - button: `label_display` を必須。`label_display` が `icon_only` なら `accessible_name`・`tooltip`・`icon` を必須。`narrow`・`confirm`・`feedback`・`shortcut` を記載できる
  - toggle: `toggle_state` を必須
  - tabs: `tabs`・`retained_state` を必須
  - nav・sidebar・pane: `panes`・`retained_state`（選択とスクロール）を記載できる
  - table: `table`・`retained_state` を記載できる
  - table_column: `sortable`・`pinnable`・`hideable`・`narrow` を記載できる
  - dialog・popover: `close`・`initial_focus`・`return_focus` を必須
  - input・select・textarea: `icon`・`label_display` を禁止。label: `confirm` を禁止
- 画面全体の欄（`retained_state`・`panes`・`shortcut`・`leave_guard`・`screen_type`）を追加し、`screen_type` ごとに必須の要素の `kind` を `if` / `then` で検査する
- 保持する状態の欄は、[規約『入力と文言』の画面設計に記載する保持](id:ui-input-wording#retention-design-01) の要素に記載を求め、保持しない要素は保持しないことを記載できる構造にする。キーの書式は [Web Storage のキーの付け方](id:ui-input-wording#storage-key-01) を参照する
- 部品設計に `persisted_state[]`（画面設計の保持と同じ構造）・`states[].viewport`（`desktop`・`mobile`）を追加し、`accessibility` を読み上げ名の要否・アイコンだけの形状を持てる構造にする
- 欄ごとの `x-rules` から、[#604](https://github.com/shuhei1101/knowledge/pull/604) で追加した規約（スプリッター・上タブを戻ったときのページ・アイコンの既定・Web Storage のキー・画面設計に記載する保持）と Issue の表の規約の項目を参照する
- スキーマの `examples` を新規の欄と必須・禁止に合わせ、テンプレート（`template-screen-design`・`template-component` と Markdown のテンプレート）を再生成する
- レビューの観点（`checksheet-review-mock-html`・`checksheet-review-implemented-screen`・`checksheet-review-component`）を、新規の欄のとおりかを確認する観点にする
- 既存の画面設計書が検査で落ちるため、マージの後に `design-schemas/v*` のメジャーを上げたタグを作る
- タグを作った後、画面設計書・部品設計書を持つ監視対象の各プロジェクトを洗い出し（起票の時点で `docs/screen/`・`docs/component/` を持つプロジェクト）、プロジェクトごとに次の内容の Issue を起票する
  - 新規のスキーマで、そのプロジェクトの全ての画面設計書・部品設計書を記載し直す（新規の欄を埋める）
  - 記載し直す途中で気づいた漏れ・誤り・より良い設計は、その場で設計を修正し、実装とテストまで合わせる
  - aituber の Issue は、[#312](https://github.com/shuhei1101/aituber/issues/312)・[#313](https://github.com/shuhei1101/aituber/issues/313)・[#314](https://github.com/shuhei1101/aituber/issues/314) を新規のスキーマで記載した共通のレイアウトの設計書を元に修正することを含める
- マージの前に、[Issue #602](https://github.com/shuhei1101/knowledge/issues/602) の「やりたいこと」と修正した内容を突き合わせ、ずれが無いことを確認する
