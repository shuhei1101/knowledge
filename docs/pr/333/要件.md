# 要件

## 要望

インターフェース定義の `flows[].flow` とモジュール構成の `diagrams[].diagram` を mdmark の図で記載し、テンプレート『インターフェース定義』『モジュール構成』と `docs/interface/`・`docs/module/` の設計書に map の外の Mermaid の図が残らない。

### スキーマ

- `schemas/design/interface.schema.yaml` の `flows[].flow` を、`common.schema.yaml#/$defs/mermaid` の参照から `$defs/map` の参照にする（シナリオの `flow` と同じ型）
- `flow` の `description`・`x-rules`・`x-used-by` を map の書き方に合わせる（`sequenceDiagram`・1 図 = 結末 1 本の一本道・登場人物と線の決まりは保つ）
- `interface.schema.yaml` の記載例（`examples`）の図を map で記載し直す
- `schemas/design/module.schema.yaml` の `diagrams[].diagram` を mdmark の図で記載する型の参照にし、`description`・`x-rules`・`x-used-by` を合わせる
- `common.schema.yaml` の `$defs/mermaid` は、参照が無くなるので削除する

`未確定`: モジュール構成の `diagrams[].diagram` を記載する mdmark の図（決める段: ドキュメント修正）

mdmark の map が描けるのは Mermaid の 1 行目が `flowchart` か `sequenceDiagram` の図で、今の `classDiagram` は描けない。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | map の `flowchart` で記載する。要素をノード、依存を矢印にし、要素の関数・属性はノードのラベルか補足（`map-data` の `notes`）に入れる | シナリオ・インターフェース定義と同じ `$defs/map` を参照でき、今の mdmark で描ける | クラス図の区画（名前・メンバー）の見た目は無くなる |
| B | mdmark の map に `classDiagram` を足す Issue を起票し、入ってから map の `classDiagram` で記載する | 今の図の記載方法を保てる | mdmark の変更を待つ間、この PR が止まる |

推奨: A

構成図で読み取るのは要素どうしの依存の向きで、メンバーの一覧はモジュール構成の `functions`・`data_models` の節が持つ。

### 設計書

- `docs/interface/` の全ての設計書の `flows[].flow` を map で記載し直す。図の中身（登場するもの・やり取りの順番）は変えない
- `docs/module/` の `diagrams[].diagram` を持つ設計書（`MOD-148-1`・`MOD-72-1`）の図を、決めた mdmark の図で記載し直す。図の中身（要素と依存の向き）は変えない

### テンプレート

- `scripts/build_templates.py` で `docs/template/template-interface.yaml`・`docs/template/template-module.yaml` を生成し直す

### 確認

- 全ての文書の検査（`scripts/check_all.py`）が通る。map の ```mermaid のブロックは maid の検査の対象になる（今のインターフェース定義の `flow` は囲みを持たず、検査の対象外）
- 書き直した map を mdmark の点検に通し、ずれが無い

### 設計書のスキーマのタグ

- 既存のインターフェース定義・モジュール構成が新しい記載方法と合わなくなる変更なので、`design-schemas/v*` のメジャーを上げる（今の最新は `design-schemas/v7.0.1`）
- タグは [#272](https://github.com/shuhei1101/knowledge/pull/272) と同じく、この PR を develop へマージした後に planner が develop の squash commit へ打つ（反映作業）
