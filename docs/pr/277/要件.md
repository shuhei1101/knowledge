### #229 精度評価とエージェントの Mock

- 判定フローチャート『精度評価をするか』（`docs/flowchart/flowchart-accuracy-evaluation.yaml`）を新設する。LLM・意思決定モデルを使用するノードを入口にし、出力が利用者・視聴者に届く生成物で、出力の良し悪しを基準で比べられ、モデル・プロンプトを差し替える見込みがあるノードだけを「精度評価をする」に至らせる。エージェント（Claude Code のエージェント・サブエージェント・スキル）は精度評価をしない
- E2E・結合テストでは、Claude Code のエージェント・サブエージェント・スキルを外部 I/O と同じく決めた動きだけをする Mock にし、エージェントの判断はテストしない決まりを、次の規約に追加する
  - Python の規約『テストレイヤー』（`python-testing-layers`）の 4 種類のテストの比較の表の結合テストの行と、「実環境で確認」とする E2E テストの行
  - Python の規約『結合テストの Mock パターン』（`python-testing-mock`）の Mock の方式の比較の表に、エージェントの行
  - 規約『E2E テスト（Playwright）』（`testing-core-e2e`）の「外部 I/O はモックに切り替える」の対象に、Claude Code のエージェント
- 新しい判定フローチャートを `rules.yaml` に掲載するかは、規約『ルール索引への登録』の強制注入の 4 つの基準で判定する。精度評価の判定フローチャートは、適用する glob を狭くできるファイル（精度評価の設計書）が develop に無いので掲載しない

### #231 機能を呼ぶインターフェースと手順の指定方法

- 判定フローチャート『機能を呼ぶインターフェースの選び方』（`docs/flowchart/flowchart-interface-choice.yaml`）を新設し、機能を呼ぶインターフェース（フック・スキル・MCP ツール・API・CLI）と、新しい手順の指定方法（エージェントフロー・サブエージェント・スキル）を 1 枚で判定する。スキルにする条件は、この 1 か所だけに持つ
  - 入口で「エージェントに複数の工程を順に進める手順を指定するか」を質問し、YES は手順の指定方法の判定（A-110）、NO は機能を呼ぶインターフェースの判定（shuhei1101/ai-monitor#2109 の一案）へ分ける
  - 手順の指定方法: 手順は原則エージェントフローにしてエージェントが MCP で参照する。サブエージェントにするのはレビュー（敵対的な検証）だけ。スキルは起動の仕組み（システムプロンプト・エージェントフローの索引）で指定できない特別な理由があるときだけ
  - 処理の本体はどのインターフェースでも関数か CLI に配置し、インターフェースはそれを呼ぶだけにする。1 つの処理にインターフェースは 1 つを原則にする
  - 判定フローチャート『エージェントに渡す文・処理の置き場所』（常に守る決まり・前提の置き場所）・『MCP・フックの渡し方』（作った MCP・フックをセッションへ指定する方法）と質問の境を注記で分け、互いに参照する
- 規約『MCP サーバー作成ルール』（`claude-mcp`）の概要から、新しい判定フローチャートを参照する
- 規約『注入文の書き分けと書き方』（`claude-context-placement`）の置き場所ごとに書くことの表で、スキルの行を「起動の仕組みで指定できない特別な理由があるときの手順」に修正し、エージェントフローの行を追加する
- 規約『サブエージェント委譲ガイド』（`claude-subagent`）の委譲の判断基準の表と、新しい判定フローチャートの質問の境（手順そのものをどれにするかと、手順の中の工程を委譲するか）を決め、食い違う行を D-273 A に合わせて修正する
- 新しい判定フローチャートを `rules.yaml` に掲載し、フック・MCP・スキル・プラグインのファイルに適用する

`未確定`: 規約『サブエージェント委譲ガイド』の委譲の判断基準の範囲（決める工程: ドキュメント修正の前に、ユーザーへ確認する）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 委譲の判断基準を、手順の中の工程を委譲するかの判定として残し、「手順そのものをサブエージェントにするのはレビューだけ」の行を新しい判定フローチャートへの参照で加える | 単純な変換・並列実行・コンテキストの圧迫の回避で工程を委譲する今の使用方法が変わらない | 工程の委譲の基準と手順の指定方法の基準が 2 か所に分かれる |
| B | 工程の委譲も「レビューだけ」に狭め、委譲の判断基準の表の委譲する行をレビューの行だけにする | サブエージェントにする条件が 1 か所になる | 単純な変換・並列実行での委譲ができなくなり、要件が変わる |

推奨: A

D-273 A が決めたのは新しい手順の指定方法で、手順の中の工程の委譲までは決めていない。B は今の委譲の使用方法を止める要件の変更になる。
