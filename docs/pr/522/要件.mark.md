# 要件

## 要望

FastAPI の規約に、MCP のツールと同じデータ（同じスキーマ）を返却する API の扱いを追加し、その API が JSON のキーとエラーの応答を MCP のツールに合わせても規約に違反しないようにする。

| 項目 | 内容 |
| --- | --- |
| 対象の API | MCP のツールと同じデータ（同じスキーマ）を返却する API。画面だけが使用する API は対象にしない |
| JSON のキー | 対象の API は、MCP のツールと同じキー（snake_case）のまま返却してよい。対象でない API は、今までどおり camelCase |
| エラーの応答 | 対象の API は、MCP のツールと同じ構造（例外の名前・メッセージ・該当した箇所）の JSON を、HTTP のステータスコードと一緒に返却してよい。対象でない API は、今までどおり RFC 9457 |
| 判定 | 「MCP のツールと同じデータか」を、規約の条件か判定フローチャートで判定できる |

終了の条件は次の 3 つ。

- 規約『入出力 Pydantic スキーマ』の camelCase の決まりに、対象の API ではキーを snake_case のまま返却してよいことと、判定の参照がある
- 規約『認証と例外ハンドラ』の RFC 9457 の決まりに、対象の API では MCP のツールと同じ構造のエラーを返却してよいことと、構造を RFC 9457 で返却する場合の拡張のメンバーとの対応がある
- 「MCP のツールと同じデータか」の判定が 1 か所にあり、2 つの規約がそこを参照している

`未確定`: 判定の表し方（決める工程: ドキュメント修正）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 規約『入出力 Pydantic スキーマ』に判定の条件の項目を 1 つ配置し、規約『認証と例外ハンドラ』から参照する | ページが増えない | 判定の軸が増えたときに、項目の文が長くなる |
| B | 判定フローチャートを新規作成し、2 つの規約から参照する | 判定の軸が増えても図で追える | 判定の軸が 1 つのうちは、質問 1 つの図になる |

推奨: A

判定の軸は「同じスキーマのデータを MCP のツールでも返却するか」の 1 つで、判定フローチャート『決まりの表し方の選び方』で判定フローチャートにならない見込みのため。ドキュメント修正の工程で、同フローチャートで判定して確定する。
