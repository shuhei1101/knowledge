# 要件

## 要望

ai-monitor の develop（[cadf7db6a](https://github.com/shuhei1101/ai-monitor/commit/cadf7db6a)）の設計書のスキーマを、knowledge の正本として移す。

| 項目 | 要件 |
| --- | --- |
| 移すスキーマ | `dev/テンプレート/*.schema.yaml` のうち、AI Monitor を前提にしない 17 件（ER図・index・アーキテクチャ図・インターフェース定義・シナリオ・テスト実行方法・データフロー・モジュール構成・共通・外部API・外部ライブラリ・状態遷移・画面設計・設定・部品設計・開発コマンド・非機能要件）。`フェーズ.schema.yaml` は AI Monitor のエージェントのフェーズの書式なので移さない（[#170](https://github.com/shuhei1101/knowledge/issues/170) のテンプレートの No 3 と同じ判定） |
| AI Monitor 固有の記述 | 移したスキーマの `title`・`description`・`examples` に、AI Monitor のエージェント名（planner・reviewer・tester）・作業 PR・release ブランチ・モニターの設定・エージェントのドキュメント索引を残さない。`grep` で 0 件になることを確かめる |
| ずれの取り込み | 各プロジェクトのコピーのうち ai-monitor に無い有用な変更を取り込む。11-05 に照合した結果、取り込む変更は無い（下の表） |
| 検査 | 移したスキーマが JSON Schema 2020-12 のメタスキーマに合い、`$ref` が全て解決でき、各スキーマの `examples` がそのスキーマに合うことを、CI の全ての文書の検査で確かめる |
| リビジョン | 各プロジェクトが `dev-docs.yaml` の `schema:` で指すリビジョンとしてタグを付ける。スキーマを変えたらタグを上げる |
| ai-monitor#2705 | 正本を ai-monitor に置いて knowledge へ Markdown を書き出す Issue で、この決定と向きが逆になる。人が読むテンプレートの生成は [#163](https://github.com/shuhei1101/knowledge/issues/163) が持つので、#163 へ統合した旨をコメントして閉じる |

### 各プロジェクトのコピーの照合

ai-monitor の develop の各スキーマと、各プロジェクトの develop の `dev/テンプレート/*.schema.yaml` を比べた。
差分は全て、ai-monitor で後から入った変更（設計書の ID・`dev-docs の画面`・実機での確認の削除・implementer の統合 等）が入る前の古い記述で、取り込む変更は無い。

| プロジェクト | 一致 / 件数 | 差分の中身 |
| --- | --- | --- |
| knowledge | 12 / 18 | フェーズ・モジュール構成・共通・画面設計・部品設計・非機能要件。古い呼び名（開発ドキュメントサーバー・implementer）と、ai-monitor#3161 で削除した実機での確認の記述 |
| voice-paste | 14 / 18 | knowledge と同じ差分のうち 4 件 |
| dev-docs・alias-inject | 1 / 18・1 / 19 | 設計書の ID（ai-monitor#3038）が入る前の記述 |
| mdmark・rule-inject・claude-balancer・shuhdev-gateway・observability | 0 件一致 | 同上 |
| mindmap・aituber | 0 件一致 | 同上に加え、ai-monitor#2068 より前のテスト実行方法の `lint` 層・画面設計の部品の参照が無い記述 |

claude-balancer の `規約.schema.yaml` と mdmark・claude-balancer・alias-inject の `files.schema.yaml` は、knowledge の `schemas/rule.schema.yaml`・`schemas/files.schema.yaml` のコピーで、設計書のスキーマではない。

### タグ

設計書のスキーマだけのタグ `design-schemas/v{メジャー}.{マイナー}.{パッチ}` を、スキーマを変えた release が master へ入った後に、そのマージの commit へ作成する。
この PR では `design-schemas/v1.0.0` を作成する（反映作業『設計書のスキーマのタグの作成』）。
上げる桁は、既存の設計書が検査を通らなくなる変更（必須のキーの追加・キーの削除・制約を狭める）はメジャー、通ったままの変更（任意のキーの追加・制約を広げる）はマイナー、`description`・`examples` など検査の結果を変えない変更はパッチにする。
knowledge のリリースのタグ（`v0.3.0` 等）はスキーマを変えていないリリースでも上がるため使わない。スキーマの変更とタグが 1 対 1 になり、各プロジェクトは上げる必要のあるときだけタグを上げる。
