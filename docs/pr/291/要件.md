## 要望

子 Issue ごとの終わりの条件（親 Issue #290 の本文から写す）。

| Issue | 終わりの条件 |
| --- | --- |
| #256 | `dev-docs.yaml` の設計書と目次の `documents[]` の行に `validators`（`ai-monitor-checks`）と `after_write`（`ai-monitor-publish`）があり、`write_docs` で設計書を書き込んだときに AI Monitor の設計書の検証と `docs/{種類}/index.yaml`・`README.md` の作り直しが走る |
| #259 | `terms.yaml` があり、`dev-docs.yaml` に用語の `alias_type` の行があって配信され、判定フローチャート『用語の登録』で knowledge に登録すると判定した呼び名が登録されている |

| #283 | `dev-docs.yaml` の設計書の行の `schema` が原本の `schemas/design/` を指し、`schemas/` 直下の設計書のスキーマのコピーと `schemas/conversions/` が無い（`ai-monitor-version.ini` は残す）。knowledge 自身の設計書から #266 で削除したキー（`issue`・`callers` など）が除かれ、`scripts/check_all.py` が違反 0 件で通る。LAY-72-1 の `schemas/` のエントリも合っている |

要件として次を満たす。

- `dev-docs.yaml` の設計書の行（architecture・nonfunctional・scenario・interface・module・library・test_procedure・dev_command・layout）と目次（index）の行の `schema` が `schemas/design/{種類}.schema.yaml` を指す（`dev_command`・`test_procedure` はファイル名の区切りがコピーと違うため行ごとに置き換える）
- 同じ行に `validators: [ai-monitor-checks]` と `after_write: [ai-monitor-publish]` があり、`write_docs` で設計書を書き込むと AI Monitor の設計書の検証が違反を返し、目次の `index.yaml`・`README.md` が作り直される
- 冒頭の説明文（`instructions`）の設計書の書式の置き場所が `schemas/design/` になっている
- 用語集は規約『ドキュメント管理』のフォルダの例のとおり `docs/terms.yaml` に置き、knowledge が原本のスキーマで検査する。`dev-docs.yaml` の用語集の行は `records: terms`・`alias_type: term` を持つ
- 用語集には、[#259 の要望](https://github.com/shuhei1101/knowledge/issues/259) の呼び名（AI slop・判定フローチャート・配信元・表し方 など）と、[shuhei1101/gui-support#108 からの連絡](https://github.com/shuhei1101/knowledge/issues/259#issuecomment-6792819347) の「A.I.VOICE 2」（別名「A.I.VOICE2」）を、判定フローチャート『用語の登録』で判定して登録する
- `schemas/` 直下の AI Monitor の配布物のコピーのうち、設計書のスキーマとそれらが `$ref` で指す `common.schema.yaml`、`schemas/conversions/` を削除する。`ai-monitor-version.ini` は配布物全体の準拠バージョンのため残す
- `scripts/check_all.py` が違反 0 件・終了コード 0 で通る

`未確定`: knowledge から AI Monitor の設計書の検証（`ai_monitor.design_docs`）を呼ぶ方法（決める段: インターフェース定義設計）

AI Monitor の `dev-docs.yaml` は作業場所で `PYTHONPATH=src` を付けて `python -m ai_monitor.design_docs` を実行しており、knowledge の作業場所からはそのまま呼べない。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | knowledge の `scripts/` に、AI Monitor のクローンの場所を環境変数で受けて `ai_monitor.design_docs` を子プロセスで呼ぶ入口を置き、`dev-docs.yaml` の `validators`・`generators` はその入口を指す | dev-docs を使う端末には AI Monitor のクローンがあり、ネットワークを使わない | 環境変数が無い端末の扱い（検証を飛ばすか失敗させるか）を決める必要がある |
| B | `dev-docs.yaml` の `run` に `uvx --from git+https://github.com/shuhei1101/ai-monitor@{タグ}` で AI Monitor を取って呼ぶコマンドを書く | 端末の設定が要らない | 書き込みのたびに取得が走りうる。AI Monitor が CLI の入口を配布していることが前提になる |

推奨: A

knowledge の書き込みは AI Monitor のクローンがある端末で行い、書き込みのたびに外部から取得すると遅くなるため。
