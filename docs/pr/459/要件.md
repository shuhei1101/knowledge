# 要件

## 要望

文書の Markdown への変換（IF-72-2）で、種類に固有のキーのうち入れ子のものを、スキーマの定義に沿って描く。
種類によらず、スキーマの `properties`・`items`・`$ref`（`$defs`）をたどって入れ子のキーの `title` を参照する。

- 入れ子のオブジェクトの中の配列（ノウハウの `scenes.fits`・`scenes.misfits`）を、JSON の文字列ではなく箇条書きで描く。オブジェクトのキーは JSON の文字列ではなく、スキーマの `title`（有効な場面・有効でない場面）で出す
- オブジェクトの配列の表（ノウハウの `cases[]`・`evidence[]`、スキルの `arguments[]`）の列名に、要素のスキーマの `title`（作品・場面・内容・出典の略号・話し手）を使用する。スキーマに `title` が無いキーは、キー名のまま出す
- 変換の結果のどこにも、値が `[` か `{` で始まる JSON の文字列が出ない
- 変換が失敗する条件（終了コード 1）と、`HIDDEN_KEYS`・項目・関連・出典の出し方は変えない

`未確定`: 列挙の値の出し方（決める工程: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 値のまま出す（`reference`・`low`） | スキーマの `description` の記載方法に依存しない | 値の意味は画面で分からない |
| B | 値に、スキーマの `description` から意味を添える | 画面で値の意味が分かる | `description` は値ごとの説明を構造で持たず、文から値の意味を切り出す決まりが必要になる |

推奨: A

スキーマは値ごとの意味を `description` の文で持つだけで、構造で参照できる場所が無い。
意味を添えるには、スキーマに値ごとの説明のキーを追加する変更が必要になり、要望の範囲（変換だけを修正する）を超える。
