# 要件

## 要望

設計とレビューで、件数に比例して繰り返す処理を追加する変更を見つけ、想定する最大の件数とその件数での上限が決定していない変更を合格にしないようにする。

| 項目 | 内容 |
| --- | --- |
| 引き金 | 変更が、要素・文書・ファイル・行の数に比例して繰り返す処理（ループの中の画面の読み書き・通信・ファイルの読み込み、要求ごとの全件の読み込み）を追加する |
| 引き金に該当するときに求めるもの | 想定する最大の件数・その件数での上限（時間か回数）の非機能要件への記載・その件数で確認するテストの 3 つ |
| レビューで確認するもの | 処理が重いかではなく、3 つがあるか |

終了の条件は次の 2 つ。

- 設計書（インターフェース定義・モジュール構成）のレビューのチェックシートに、引き金に該当する設計で最大の件数と上限の記載を求める行がある
- 実装・テストコードのレビューのチェックシートに、引き金に該当する差分で最大の件数で上限を確認するテストを求める行がある

`未確定`: 最大の件数と上限の記載先（決める段: ドキュメント修正）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 判定フローチャート『非機能要件のレイヤー』の結果に従う（1 コンポーネントで閉じる値はその変更の計画、またぐ値は非機能要件の設計書） | 既存の判定と食い違わない | チェックシートの行から判定フローチャートを辿る手間が増える |
| B | 常に非機能要件の設計書に記載する | 記載先が 1 つで探しやすい | 1 コンポーネントの中で閉じる値をシステムレベルに配置することになり、判定フローチャートと矛盾する |

推奨: A

画面の応答時間のように 1 コンポーネントで閉じる値は、判定フローチャートがサブシステムレベルに配置すると定めているため。
