# 要件

## 要望

規約『コンテンツの置き場所』に、`data/` に配置する大きいファイル（音声・画像・動画）を、端末を移したとき・失ったときに復元する方法を記載する。
記載を読めば、新しい端末で `data/` の大きいファイルを元の状態に戻す手段が 1 つに決まる。

`未確定`: 復元の方法（決める段: ドキュメント修正の前にユーザーへ確認する。費用・外部サービスの利用に関わるため）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 大きいファイルだけを持つ別のリポジトリ（Git）に配置し、clone で復元する | Git の操作だけで復元でき、履歴も残る | 差分を確認しないファイルで履歴が膨らみ、ホスティングのリポジトリの容量の上限に当たる |
| B | Git LFS で同じリポジトリに配置し、`git lfs pull` で復元する | メタデータの YAML と同じリポジトリで、clone と同じ流れで復元できる | LFS の容量と転送量の上限を超えると費用が発生する |
| C | `data/` をクラウドストレージのバックアップ先へ同期し、同期し直して復元する | Git の容量に影響せず、同期し直すだけで元の状態に戻る | 同期のツールとクラウドストレージのアカウントの用意が要る |
| D | メタデータの YAML にファイルの取得元（URL・生成の条件）を記載し、取得し直して復元する。取得し直せないファイルは C で残す | 取得し直せるファイルは保管先が要らない | 取得元の消失・生成の結果の揺れで同じファイルに戻らないことがあり、C も併用する |

推奨: C

音声・画像・動画は差分を確認しないため、Git の履歴に残す利点が無い。C は Git の容量の上限に当たらず、同期し直すだけで元の状態に戻る。
