| 案 | 内容 | メリット | デメリット |

| A | 外部 API の `endpoints[].request[]`・`endpoints[].response[]` と、外部ライブラリの `catalogs[].entries[]`（設定のキーを含む対象）・`catalogs[].entries[].params[]` に、省略できるキー `verification`（`verified`・`docs_only`・`unverified`）と `verified_at`（日時）を並べて追加する。型は `common.schema.yaml` の `$defs.verification_state`・`$defs.verified_at` に 1 つずつ持つ。API・ライブラリ全体の `verification` は残す | 表の行の 1 キーが 1 列になり、確認の状態と確認日時の列がそのまま出る。既存の設計書がそのまま通る | 全体の状態とパラメータごとの状態が食い違いうる |
| B | 案 A のキーを `verification`（`state`・`verified_at`）のオブジェクトにまとめる | 後から確認の方法などのキーを同じオブジェクトに追加できる | 表のセルにオブジェクトが入り、確認の状態の列を出すには描画の側の対応が要る |
| C | 案 A に加え、API・ライブラリ全体の `verification` を削除する | 状態の持ち場所が 1 つになる | 既存の設計書が通らなくなる破壊的変更になる |

推奨: A

表に確認の状態の列を出すという要望を、描画の側を変えずに満たせる。全体の動作確認（日時と内容）は、パラメータの状態とは別の情報として残る。
