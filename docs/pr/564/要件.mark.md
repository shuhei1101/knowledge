# 要件

## 要望

直下の `project-index.yaml` の `direct_commit.kinds[]` に、dev-docs のメタデータの画面から直コミットしてよい knowledge の種類を追加する。

| 要件 | 終了の条件 |
| --- | --- |
| 管理用の YAML の種類 | `files.yaml` を配信する種類（`skills`・`scripts`・`plugin`・`tests`・`schemas`・`docs_folder`・`root`）が `direct_commit.kinds[]` にある |
| 規約などの種類 | 下の `未確定` で決めた種類が `direct_commit.kinds[]` にあり、決めなかった種類は無い |
| テンプレートとスキーマ | `template` と、スキーマの原本（`schemas/`）は直コミットの対象にしない |
| 説明の追随 | 配信元の設定の `instructions`・README・アーキテクチャ図・シナリオの、直コミットできる種類の記載が `direct_commit.kinds[]` と一致する |

`未確定`: 規約など、本文を持つ文書の種類（`rule`・`flowchart`・`decision-table`・`checksheet`・`guide`）を直コミットの対象に追加するか（決める工程: 単一ユースケース設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 管理用の YAML の種類だけを追加し、規約などの種類は #536 の決定のまま追加しない | エージェントの `write_docs` から、規約の本文がレビューを経ずに変わることが無い | 規約などのタグ・別名を、画面から修正できない |
| B | 管理用の YAML の種類に加えて、`rule`・`flowchart`・`decision-table`・`checksheet`・`guide` を追加する | 画面で規約などのタグ・別名を修正できる。dev-docs#310 の決定（規約の本文は行の追加と文言の修正だけ）に合う | 許可は種類の単位のため、エージェントの `write_docs` からは本文も制限なく直コミットできる。行の追加と文言の修正だけに留めるのは、画面の項目の絞り込みとスキルの手順に頼る |

推奨: B

画面のサーバーが送信する項目をメタデータのキーに絞るため、画面からの修正は dev-docs#310 の決定の範囲に収まる。
ユーザーが直コミットで特にしたいのは別名・タグなどのメタデータで、knowledge の別名の多くは規約などの文書が持つ。

`skill`・`changelog`・設計書の種類（`scenario`・`interface` など）・目次（`index`）は、案によらず追加しない。
`skill` はスキルの工程、設計書は AI Monitor の設計を持ち、どちらも作業 PR のレビューで変える。
