### #215 の要件

- 新しい規約 `dev-design-doc-purpose` に目的と守ることを表で記載し、`aliases` に「設計」「設計書」を置いて dev-docs の `term` で引けるようにする
- `schemas/design/` の全てのスキーマのキーについて、`description`・`x-rules`・`x-used-by`（[#266](https://github.com/shuhei1101/knowledge/pull/266) で入った使用先）から「そのキーで考えさせること」が読み取れるかを点検し、読み取れないキーの記載を直してテンプレートを生成し直す

### #225 の要件

- 判定の順と結果は Issue の `## 決まったこと`（A-79）のとおりにする
  - 判定: ファイルのエントリか → 直下にファイルを持たないフォルダか → 直下のファイルは同じ役割を持つか → 1 つの機能だけが参照するか → 機能ごとに分けたフォルダか
  - 結果: 役割と機能の単語を付ける・役割の単語だけ・機能の単語だけ・付けない・役割か機能でフォルダを再分割する
- 書式は knowledge の判定フローチャートのテンプレート（`template-flowchart`）に合わせる
- `layout.schema.yaml` の `entries[].content_types` からこの判定フローチャートを ID で指し、`scripts/build_templates.py` で `docs/template/template-layout.yaml` を生成し直す

### #232 の要件

- レベルの共通の定義は影響で判定し、名前と数値は OpenTelemetry の SeverityNumber に揃える。本番でも INFO 以上を観測基盤へ送る
- 観点（本番障害・外部連携・お金・セキュリティ・監査・データ整合・性能・監視の経路）× レベルの表と、ログを出すか・どのレベルかの判定フローチャートを置く（一案は shuhei1101/ai-monitor#2328 の本文）
- 書き方の決まり: 出してはいけないデータ・固定のイベント名・例外は 1 回だけ記録・OpenTelemetry の命名
- 言語ごとのロガーの規約（`python-shared-logger`・`react-shared-logger-implementation`）のレベルの表は共通の規約を指し、言語のレベル名との対応だけを残す
- ログのレベルを決めている他の箇所（`python-fastapi-auth-error` の『認証失敗のログレベル』・`python-llm-exception-retry` の『リトライ時のログ』・判定フローチャート『フォールバック』の ※4・※5）を共通の規約と突き合わせ、食い違えば共通の規約を指す形に直す（task-reviewer の任意の指摘）
